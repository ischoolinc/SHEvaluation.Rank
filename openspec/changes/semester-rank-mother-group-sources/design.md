# Design

## Context

見 `proposal.md` 的 Why。現況集中在 `CalculateSemesterAssessmentRank`。計算學年期被固定成系統預設值。確認前的表格把五種母群放在欄位索引 4 到 8，計算用索引取值，學生 ID 放在列的 `Tag`。

`rank_batch.setting` 目前由 `XmlDocument` 產生，實際結構是：

```xml
<Setting 學年度="114" 學期="2" 考試名稱="學期成績"
         不排名學生類別="" 類別一="" 類別二="">
  <年級>1</年級>
  <擇優採計成績>原始成績</擇優採計成績>
</Setting>
```

學校設定「固定排名_學期成績排名計算」是另一份 XML，只含 `<擇優採計成績>`，在按下計算時寫入。檢索畫面不解析 `setting`。

新批次的母群快照不寫進 `rank_batch.setting`。它與計算設定同一個 `INSERT`，寫入既有 `rank_batch.extension` JSONB 陣列，`extension_name` 為 `MotherGroupSnapshot`。舊批次 setting 裡的 XML 快照仍可讀；兩種都沒有時才讀 `rank_batch_student`。

學期排名的 `rank_batch_student` 沒有科別與參與旗標，而且由有成績的 `score_list` 寫入、沒有去重。科別只存在科排名 `rank_matrix.rank_name`。完全沒有成績的學生不會留在舊批次。

`QueryHelper` 只有 `Select`。年級 SQL 失敗目前被吃掉，批次 ID 失敗時會留在 0，畫面仍可能顯示計算完成。

## Goals / Non-Goals

**Goals:**

- 三種來源先變成同一份確認清單。每次計算在畫面執行緒複製一份獨立工作副本，排名 SQL、快照與擇優片段只讀這份副本。
- 參與旗標進入既有排名窗口的分組，不另寫一套排名公式。
- 新批次能用 `rank_batch.extension` 的 JSONB 快照完整還原確認清單。`setting` 只保留學年度、學期、考試名稱、不排名類別、類別、年級與擇優設定。
- 全部年級成功後才公布；失敗時舊的有效排名仍可檢索。

**Non-Goals:**

- 不改定期評量、技職繁星與排名檢索的資料表契約。
- 不新增資料表或排名欄位。
- 不在確認畫面修改五種母群名稱。
- 不在確認前提前統計有分數人數。
- 不修正舊版重複科目被計多次的行為。
- 不把已記錄的三項歷史來源遺留併入載入狀態、寫入保護、測試驗證或開放寫入。
- 不在 PostgreSQL 9.6 與 17.1 的必要證據完成前開放實際排名寫入。

## Decisions

### 1. 畫面分成條件、確認、計算

條件畫面保留年級、不排名類別、類別一、類別二、擇優採計。新增來源選擇，預設「依目前學生資料產生」。開啟時學年度與學期為系統目前值。目前學生來源沿用既有政策，恢復系統期間並停用這兩個欄位。歷史與 Excel 才可編輯計算期間。不另查成績學年度清單。歷史期間與批次選取不得額外改寫計算期間；切換來源仍依各來源原有政策處理。

確認畫面取代現有唯讀學生表作為計算前的最後一步。欄位綁定學生 ID 與明確欄名，不再用欄位索引對應母群。母群名稱唯讀。參與使用可勾選欄，並提供多選右鍵。搜尋只過濾顯示列，不改清單內容。還原把參與狀態回到進入確認畫面時的初始值。

歷史來源才顯示「加入學生」。這條路徑目前仍只以學號查詢，和 Excel 的學號加學生狀態不同。同一學號有多位學生時不加入。確認清單裡已經有不同 `student.id`、學號卻相同時，既有去重也可能把另一位看成已在清單。這次不改 Task 5.5。日後若調整，確認清單內以 `student.id` 為唯一識別。

替代方案是繼續使用現有唯讀表並在計算時才套規則。無法滿足計算前調整參與，因此不採用。

### 2. 同一筆母群資料與優先順序

每名學生有原始副本與工作副本。每種排名有一個名稱與一個參與值。排名種類沿用資料庫既有文字：`年排名`、`科排名`、`班排名`、`類別1排名`、`類別2排名`。

初始清單的優先順序：

1. 三種來源先建立來源原值。歷史快照的原值就是快照內的名稱與參與狀態。無快照歷史資料只從該批排名資料還原。目前學生與 Excel 使用各自來源產生的名稱與參與狀態。此步驟不改名稱，也不寫回舊批次。
2. 類別一或類別二名稱空白時，該項參與設為 false。目前學生來源的科別名稱即使空白，該項參與仍為 true。
3. 三種來源接著都套用圖1不排名類別：符合者五種參與改為 false，五種名稱維持來源原值。
4. 使用者只改工作副本的參與值。進入確認清單時看到的是第 3 步之後的初始值；還原回到這個初始值。計算與匯出都讀工作副本。
5. 新批次的快照保存圖2最終值。下次把它當歷史來源時，仍先讀這份最終值，再依當時圖1的不排名類別重新產生初始參與。

目前學生來源的名稱規則維持現況：一般生、有班級、年級有值、再套勾選年級；年排名為「N年級」；班排名為班級名稱；科別為學生科別，否則班級科別；類別沿用 `First()`。不排名類別不再把學生從清單刪除。

無快照歷史來源的還原：

- 學生集合是該批 `rank_batch_student` 與 `rank_detail` 的學生 ID 聯集，學生列去重。
- 年、班、類別一、類別二優先取 `matrix_grade`、`matrix_class`、`matrix_tag1`、`matrix_tag2`；沒有學生列時改取對應 `rank_name`。
- 類別欄位空白且沒有對應類別排名，視為原本就沒有類別，不另發缺漏警示。
- 科別只取科排名 `rank_name`。名稱是空字串代表已還原的空白科別，參與為 true。沒有科排名列才算無法還原。
- 無法還原的項目名稱空白、參與 false，並在該項顯示警示。
- 還原完成後才套用三種來源共用的不排名預設。
- 同一學生、同一排名類型若出現兩個以上不同名稱，不取第一筆，也不用目前母群覆蓋。該項不選定母群、不參與，確認清單列出學生、排名類型與全部衝突名稱。相同名稱的重複列只算一個名稱。其他未衝突項目照原值還原。
- 以上讀取都不更新舊的 `rank_batch`。
- 批次層級提示：完全沒有排名資料的學生不會出現。

年排名名稱能解析出年級時，才把學生放進該年級的計算批。名稱空白時不改用目前班級年級，計算前提示並不產生該生的新明細。

替代方案是缺科別時用目前科別補上。這會把歷史母群改成現況，與已確認決策相反。

### 3. Excel 用既有 Aspose.Cells

第一列共 13 欄，姓名後面是學生狀態：學號、姓名、學生狀態、年排名母群、班排名母群、科排名母群、類別一母群、類別二母群、年排名參與、班排名參與、科排名參與、類別一參與、類別二參與。

學生狀態只接受這六個中文，並對到 `student.status`：一般是 1、延修是 2、休學是 4、輟學是 8、畢業或離校是 16、刪除是 256。空白、其他文字或其他數字都不接受，也不改寫成一般。這組對照與學期排名檢索畫面既有的狀態文字相同。

參與只接受「參與」「不參與」。學號先去掉前後空白，保留前導零。檔內重複改看學號加學生狀態；相同學號、不同狀態可以同時存在。再以這兩個欄位一起查 `student`。零筆是找不到，超過一筆是身分不唯一，都不任選。對到同一 `student.id` 的兩列也是錯誤。任一列失敗則整次匯入不建立確認清單，並回報 Excel 列號與錯誤。姓名與主檔不同時，清單採用主檔姓名與解析出的 ID，並保留警告。

`StudentMotherGroup` 目前沒有學生狀態。最小做法是加一個可空整數 `Status`，只承接 `student.status`。目前學生來源仍只含一般生，建立名單時把既有狀態抄進來。Excel 匯入把對到的那一筆狀態抄進來。排名 SQL 不讀這個值。`MotherGroupSnapshot version="1"` 不增加狀態屬性，歷史快照還原後 `Status` 可以是空的。

匯出第 3 欄前，先看每位學生的 `Status`。已有值就直接用。沒有值時，把這些 `student.id` 放進同一句 `SELECT student.id, student.status FROM student WHERE student.id IN (...)`。這是讀目前學生主檔的狀態，不是還原歷史排名當時的狀態，也不改歷史母群名稱或參與。不要逐位學生各查一次。沒有缺值就不要查。查不到該 id、查詢失敗、同一 id 超過一筆，或狀態不是 1、2、4、8、16、256，就回報該生並不產生匯出檔。不把空值寫成一般，也不用學號找狀態。

匯出寫工作副本的 13 欄。再次匯入同一份檔時，學號加狀態對回同一個 `student.id`，母群名稱取自檔案。圖1不排名類別會重新套用，所以符合者的初始參與狀態會變成不參與，與匯出檔內的參與值可以不同。使用者仍可在確認清單改回檔內的參與值。五種母群名稱與參與規則不變。這段查詢與 13 欄都不改排名 SQL、快照格式或 Task 10.2。

### 4. 排名 SQL 沿用同一列並加上旗標

排名窗口仍以年級分割，避免不同年級混在同一母群。`student_list` 每生一列，帶五個名稱與五個參與旗標，不複製五份學生清單。正式計算由 `jsonb_to_recordset` 展開這份清單。每位學生一段 `SELECT` 再 `UNION ALL` 只留在比較基準，或測試明確指定的舊夾具；正式公布入口沒有這個旗標時不得改走舊清單。若計算先寫入資料庫，那些列不得成為有效排名，也不得停用舊列。所有勾選年級的有效排名切換，都放在第 6 節那一次單一語句。

窗口分組加入對應旗標，例如年排名：

```text
PARTITION BY rank_grade_year, subject, participate_year
```

科、班、類別一、類別二比照。`COUNT`、`ROW_NUMBER` 與後續標準差、百分位、五標使用同一組參與者。寫入 `score_list` 時再保留該項參與為 true 的列。類別排名另要求名稱不是空白。科排名在參與為 true 時允許空白名稱。

沒有分數的列維持現有 `IS NOT NULL` 條件，不進入該項名次與 `matrix_count`。

`item_type`、`rank_type` 與統計欄位不改。`ref_exam_id` 維持 -1。

新 SQL 只使用 PostgreSQL 9.6 已有、17.1 仍可執行的語法：窗口函數、可寫 CTE、`FILTER`、`GREATEST`、`unnest(xpath())`。不使用 `XMLTABLE`、`PROCEDURE`、產生欄位或 `MERGE`。

### 5. 新批次快照放在 extension，舊 XML 仍可讀

新批次的 `rank_batch.setting` 只保留原有 XML 計算設定，不加入 `MotherGroupSnapshot`。學年度、學期、考試名稱、不排名學生類別、類別一、類別二、年級與擇優採計成績都留在 setting。

母群快照改寫同一個 `INSERT` 的 `rank_batch.extension`。這個欄位是 JSONB 陣列，預設 `[]`。快照是陣列中的一個物件，`extension_name` 固定為 `MotherGroupSnapshot`，`version` 是整數 1。同一個陣列只留一筆這個名稱；已有其他 `extension_name` 時原物件保留，重複建立時取代既有快照，不另插一筆。

```json
[
  {
    "extension_name": "MotherGroupSnapshot",
    "version": 1,
    "source_kind": "History",
    "source_batch_id": 145,
    "students": [
      {
        "student_id": 27893,
        "student_number": "510001",
        "student_name": "姓名",
        "grade_year": 1,
        "ranks": {
          "year": { "name": "1年級", "participate": true },
          "dept": { "name": "普通科", "participate": true },
          "class": { "name": "高一甲", "participate": true },
          "tag1": { "name": "", "participate": false },
          "tag2": { "name": "", "participate": false }
        }
      }
    ]
  }
]
```

`source_kind` 只用 `Current`、`History`、`Excel`，不寫畫面文字。`source_batch_id` 只在歷史來源寫正整數；目前學生與 Excel 寫 JSON null。`participate` 是 JSON boolean。`student_name` 要保留，因為舊 XML 有姓名。`grade_year` 只在年排名名稱能用既有規則解析成正整數時寫數字，否則寫 null，不另造年級。學生狀態與不排名類別本來就不在 XML 快照裡，JSON 也不新增；還原後狀態仍可為空，不排名類別仍依當時的圖1另套。學生清單來自確認清單工作副本，包含不參與任何排名的學生。

JSON 由程式序列化，SQL 沿用單引號跳脫後以 `'...'::jsonb` 寫入。不用 PostgreSQL 12 以後才有的 JSON path，也不把快照包成單一 XML 字串。不先插入批次再更新 extension。

讀歷史批次的順序是 extension 的 JSON 快照、setting 的 XML 版本 1、然後才是 `rank_batch_student`。JSON 快照存在但格式錯誤、版本不是 1、學生內容無法還原或同名物件重複時，停止並說明原因，不改讀 XML 或排名學生。extension 是 null、空白、`[]` 或沒有這個名稱時，才讀舊 XML。舊 XML 的 `MotherGroupSnapshot version="1"` 解析保留，學生清單就是這份 XML 的完整名單，不改查 `rank_batch_student`，也不用目前學籍補母群名稱。XML 沒有版本 1、兩種快照都不存在時，才讀該批 `rank_batch_student`，不改用目前學生。

`rank_batch_student` 的學期成績插入讀 `score_list`，沒有先對學生去重，所以同一學生可以有多列。兩種快照都不存在時，年、科、班、類別一、類別二的名稱分別讀 `matrix_grade`、`matrix_dept`、`matrix_class`、`matrix_tag1`、`matrix_tag2`。2026-11-17 起，這個讀取先確認所選批次的 `id` 唯一，再以 `id` 游標分頁；全部頁合成一份後才做既有的依學生合併。年、科、班的參與改依決策 11，不沿用欄位裡的歷史參與，空白或衝突也不跳出提示。學期成績這條插入沒有寫 `matrix_dept`，所以舊列的科別常是空白；不用 `rank_matrix` 或目前學籍把名稱補回來。

學校擇優設定照舊另存，與批次 setting 分開。

### 6. 停用與啟用必須是同一個資料庫交易

`FISCA.Data.QueryHelper` 對外只有 `Select`。組件內是 DSA 的 `SelectData` / `GetQuery`，沒有 `BEGIN`、`COMMIT` 或交易物件。每一次 `Select` 都是獨立請求，不能假設下一次呼叫還在同一個交易。因此不使用跨呼叫的 `BEGIN` / `COMMIT`，也不把多個語句用分號串成腳本。

PostgreSQL 對單一語句會整句提交或整句回復。現有排名 SQL 已證明一次 `Select` 可以執行含多個可寫 CTE 的單一語句。停用舊有效排名與啟用新排名必須放在這同一次 `Select` 的同一句裡，涵蓋本次所有勾選年級。其他連線在這句提交前仍讀到舊的有效排名；提交後才同時看到舊列失效與新列生效。這句失敗時，資料庫回復整句，舊有效排名與執行前相同。

語句內用 CTE 依賴讓停用與寫入新資料屬於同一句。停用條件是同學年度、學期、勾選年級、`ref_exam_id = -1`、`item_type LIKE '學期/%'` 且原本 `is_alive = true`。新矩陣在同一句寫入並設為有效。`rank_batch` 的 ID 由這句的 `RETURNING` 在句內使用；呼叫端沒有取得有效 ID 就不得再送寫入，禁止使用 0。

計算可以先在記憶體準備 SQL。若要在公布前把新資料寫進資料庫，那些列的 `is_alive` 必須不是 true，而且不得同時停用舊列。公布那一句才把新列設為有效並停用舊列。公布前的任一年級失敗，只清理本次尚未生效的資料，不改舊有效排名。

實作公布前先只讀 `pg_index`、`pg_constraint`。現行程式已在同一句裡把舊列設為無效並插入新列，正式環境若能完成重算，代表這種並存是可行的。目錄檢查用來確認所有勾選年級可以沿用這個方式。若唯一約束不允許舊列與新列同時存在，就停止公布並回報，不改寫舊列的 `rank_name`，也不刪除舊批次；那兩種做法都會破壞之後的歷史母群還原。

若單句因閘道長度限制無法送出，同樣停止公布並回報。不得改成逐年級各自提交有效排名。

新 SQL 只使用 PostgreSQL 9.6 已有、17.1 仍可執行的語法。不使用 `XMLTABLE`、`PROCEDURE`、產生欄位、`MERGE`，也不依賴跨請求交易。

### 7. 初次載入使用既有左下角說明

條件頁左下角的 `labelX6` 就是載入狀態的位置。原文是「說明：班、科、年排名會自動計算。分項成績擇優項目請參考成績計算規則。」不新增視窗，也不把階段留在主視窗狀態列。`pbLoading` 仍只用於之後的計算。

五個階段依序是：畫面初始化、載入學校設定、載入學生類別、載入學生清單、載入年級清單。每一段先寫入 `labelX6`，再讀取該段資料，下一段直接覆寫。五段都成功才把原文寫回，並啟用「下一步」。任一階段失敗時，錯誤留在 `labelX6`，不恢復原文，已填的類別與年級清空，「下一步」維持停用。載入期間「下一步」也維持停用。不顯示沒有依據的百分比。

目前這四段資料在建構函式的 UI 執行緒上同步讀取，對話框尚未顯示：

- `School.DefaultSchoolYear`、`DefaultSemester`，以及「固定排名_學期成績排名計算」設定檔。
- `TagConfig.SelectByCategory`。
- `Student.SelectAll()` 後以狀態一般、有班級、`Class.GradeYear` 有值篩選。
- 年級清單是學生清單的記憶體整理，在 `Load` 填入 `listGradeYear`。

設定檔有內容時先取消四個擇優核取方塊再依 XML 勾回；設定檔是空字串時維持 Designer 預設。這段與學生篩選都保持原樣。

這個儲存庫沒有 `K12.Data` 物件或其關聯屬性的執行緒安全契約。建構函式目前在 UI 執行緒使用它們。`Class.GradeYear` 是學生物件的關聯屬性，篩選必須與 `SelectAll()` 同一執行緒。核取方塊、下拉、年級清單與 `labelX6` 只在 UI 執行緒更新。`CurrentStudentMotherGroupSource` 在下一步的背景工作裡會再讀 `student.Class` 與 `StudentTag.SelectAll()`；那是既有路徑，Phase 8 不擴大它。

Phase 8 先做只讀確認。確認結果寫進該 Task 的紀錄，不把未確認的呼叫移到背景執行緒。確認可離緒時，背景工作只負責讀取，UI 執行緒負責階段文字與控制項。尚未確認時，讀取留在 UI 執行緒，並在每次讀取前把控制權交回訊息迴圈，讓 `labelX6` 先畫出該階段。不使用 `Application.DoEvents()`。這時單次查詢期間畫面仍會停住，但階段文字在查詢開始前已經可見。

替代方案是不管執行緒安全，直接把 `SelectAll()` 與 `Class` 放進 `BackgroundWorker`。關聯屬性若不是執行緒安全，篩選結果會不穩定，因此不採用。

按下下一步後，同一個 `_nextStepRunning` 擋住目前學生、歷史批次與 Excel，並立刻停用下一步。左下角沿用 `labelX6`：目前學生顯示「正在載入目前學生母群資料...」，歷史來源顯示「正在讀取歷史批次及母群資料...」，Excel 顯示「正在匯入 Excel 母群資料...」。文字寫入後呼叫既有 `PaintLoadStage()`。不新增 Label，不顯示沒有依據的百分比。

第二頁完整開啟後解除旗標，第一步的下一步維持停用。按上一步、取消選檔、驗證失敗、查無資料或例外時，恢復原本說明並重新啟用下一步。每個 `BackgroundWorker.RunWorkerCompleted` 都要走到其中一種結果，避免按鈕停住。

Excel 的 `OpenFileDialog` 留在畫面執行緒。選到檔案後，活頁簿解析、學號查詢與驗證放到背景工作；背景工作不碰 WinForms 控制項。驗證成功才顯示確認清單。歷史批次仍先 JSON、再 XML、最後 `rank_batch_student`，這次只補進行旗標與完成事件的狀態恢復。

### 8. 寫入前確認與執行中旗標

`btnCacluate_Click` 目前先碰到 `SemesterRankWriteGate.CanWriteRankTables()`。它回傳 `false` 後就返回，`cd.Save()` 與 `queryHelper.Select(insertRankSql)` 都不會執行。Phase 9 與 Phase 10 維持這個回傳值。

確認框與執行中旗標加在閘門返回之後的路徑。閘門仍是 `false` 時，使用者看到的仍是既有阻擋訊息，不會先確認再被擋下，也不會儲存組態或送出 SQL。這個 `return` 維持計算流程的第一個返回。Phase 9 與 Phase 10 維持閘門為 `false`。Task 9.3 完成前，Task 11.1 不得把閘門改成 true。

閘門將來打開後，順序是：

1. 已在執行中則直接返回。執行中旗標在年排名提示、閘門阻擋訊息與確認框之前設下。
2. 年排名名稱無法解析時沿用現有提示，不整批中止。
3. 在畫面執行緒先提交確認清單上尚未寫入的參與編輯，再建立一次計算工作副本。副本包含學生 ID、學號、姓名、五種母群名稱、五種參與狀態，以及母群衝突標記與衝突名稱。`RankSlot` 與 `StudentMotherGroup` 都是新物件，不與畫面 `_confirmList` 共用。擇優採計清單另行複製。學年度、學期、不排名類別、類別一、類別二、來源種類與歷史批次識別固定為這次讀到的值。
4. 用圖1勾選年級與工作副本可解析年排名的交集判斷。交集為空時顯示「沒有可計算的年級」並返回。不顯示確認框，不呼叫 `cd.Save()`，不產生或執行排名 SQL，也不留下這次停用的控制項。
5. 有交集才顯示確認框。年級就是這份交集。文案同時說明擇優組態會先寫入學校設定，排名語句失敗時這份組態不會回復。
6. 取消則返回，不呼叫 `cd.Save()`，不呼叫 `Select`，也不留下這次停用的控制項。
7. 確定後停用計算、上一步、五種參與核取、右鍵批次參與、還原參與，以及歷史來源的加入學生，並顯示既有 `pbLoading`。這些事件處理仍檢查執行中旗標，不能只靠 `Enabled`。
8. 其後維持 Task 4.2 已鎖定的順序：`cd.Save()`、`SemesterRankSql.Build`、母群快照 JSON、`SemesterRankPublishSql.Build`、`ApplyParticipation`、唯一一次 `queryHelper.Select`。確認框年級、排名 SQL、快照、擇優 XML 與 SQL 擇優片段都使用第 3 步的同一份副本。setting 不含快照，extension 在同一個 `INSERT`。背景工作不直接讀 `_confirmList` 或 `_GradeSelectList`。
9. 完成或失敗時清除旗標，並把第 7 步停用的控制項恢復成計算前的可用與可見狀態。原本停用或隱藏的控制項不得無條件啟用。失敗顯示失敗，不顯示計算完成。

`cd.Save()` 維持在 `Select` 之前。學校擇優設定與 `rank_batch.setting` 仍分開存放。不在開放寫入時默默把它移到成功之後；那會改掉 Task 4.2 的檢查，必須另作設計修訂。沒有可計算年級時連 `cd.Save()` 都不呼叫，因為這不是排名語句失敗，而是計算尚未開始。

三種來源進確認清單後仍共用這條路徑。新快照的 `source_kind` 是 `Current`、`History`、`Excel`。舊 XML 版本 1 仍可讀。成績期間仍是圖1。排名公式與四張 `rank_*` 表結構不變。

替代方案是只停用畫面控制項，背景工作仍讀 `_confirmList`。漏掉一個事件就會讓排名 SQL 與快照分成兩份，因此不採用。另一個替代方案是把 `cd.Save()` 移到公布成功之後；那會改變 Task 4.2 的順序，因此不採用。

### 9. 獨立測試庫與已中止交易

Phase 10 不使用正式學校資料庫，不把學校連線寫入 `App.config`，也不從學校端的 `QueryHelper` 做首次寫入。測試庫是專用的 PostgreSQL 9.6 與 17.1，結構足以容納四張排名表、成績與目錄查詢，資料是人工的少量列。

產品語句仍然是一次 `Select` 的單一語句，不送 `BEGIN`、`COMMIT` 或 `SAVEPOINT`。測試客戶端自己的連線才使用交易。

PostgreSQL 在交易中的語句失敗後會把該交易標成已中止。中止之後，除了回復交易或回復到儲存點，後續指令不能讀到驗證結果。故意失敗因此採用其中一種：

- 失敗語句前設 `SAVEPOINT`，語句失敗後 `ROLLBACK TO SAVEPOINT`，再 `SELECT` 核對，最後外層 `ROLLBACK`。
- 或讓失敗語句使用自己的獨立交易，語句錯誤由該交易回復後，另一筆交易再 `SELECT` 核對。

成功路徑在核對四張表關聯、快照、五種參與、圖1學年度與舊排名停用之後，外層 `ROLLBACK` 或獨立交易回復，不把測試排名留在庫中。兩個版本都要做成功與故意失敗。語句長度另與實際閘道上限比對；超過則停止，不改成逐年級公布。

歷史批次清單、無快照還原與 Excel 學號查詢在同一測試庫只做 `SELECT`。這些讀取通過不代表 Task 4.2、4.3、5.1 到 7.3 可以勾選。

### 10. 證據通過後才解除閘門

Phase 11 的前提是 Phase 10 的必要證據在 9.6 與 17.1 都留下，而且 Task 9.3 已完成。缺少任一項就不改 `CanWriteRankTables()`。解除時同時更新所有要求 `return false` 的 Phase 檢查，改為檢查確認框、執行中旗標、工作副本、空年級防護、單次 `Select` 與失敗不顯示成功。排名公式、擇優片段與三種母群來源規則不改。

### 11. 學生清單改由 JSONB 傳入

修改前，`SemesterRankSql.Build` 依年排名名稱解析年級，每位學生產生一列 `SELECT ... AS student_id`，`SemesterRankPublishSql` 再用 `UNION ALL` 接成 `student_list`。年級條件 `calc_condition` 另以年級之間的 `UNION ALL` 各寫一列。成績 CTE 裡的 `UNION ALL` 是科目與分項成績的合併，不是學生清單。

修改後，正式路徑只收集 `SemesterRankStudentInput`。公布語句在背景工作組 SQL 時，把這些物件寫成一個 JSON 陣列，放進同一個 `INSERT` 語句：

`student_list AS (SELECT s.student_id, ... , s.participate_tag2 FROM jsonb_to_recordset('...'::jsonb) AS s (...))`

`jsonb_to_recordset` 自 PostgreSQL 9.4 起就有，9.6 到 17 都可以用。不使用 `MATERIALIZED`、JSON Path、`JSON_TABLE` 或 `MERGE`。文字先做 JSON 跳脫，再沿用既有 SQL 單引號加倍。`QueryHelper` 沒有參數介面，所以 JSON 留在這一句的字面值裡。姓名含分號時，既有的單一敘述檢查仍會拒絕整句，這和舊版把分號放進學生 SELECT 的結果相同。

三種來源進入計算後都讀同一份 `calculationList`。目前學生、歷史快照與 Excel 不再各組一套學生 SQL。歷史來源學年度與本次計算學年度仍然分開。

JSON 欄位對應舊 `StudentSelect`：`student_id` 是 JSON number，姓名與四種母群名稱是文字，空白是 `""` 而不是 JSON null，五種參與是 JSON boolean。`student_list` 仍投影 `participate_year`、`participate_dept`、`participate_class`、`participate_tag1`、`participate_tag2`。`ApplyParticipation` 繼續以字串改寫成績 CTE，不改寫學生清單本身。

`calc_condition` 仍使用 `LimitToSelectedGrades` 之後的年級。無法解析年排名年級的學生不進 SQL，但快照仍保留。未勾選年級不進 JSON，也不進 `calc_condition`。SQL 用的 JSON 與 `MotherGroupSnapshot` 來自同一份確認清單，但不把 SQL JSON 再寫進 extension。

同一 `student_id` 出現兩次時，正式 `Build` 直接停止並提示，不取第一筆。這和舊版靜默產生兩列 SELECT 不同。確認清單的 `Add` 原本就會擋住重複；`Load` 不會。舊版比較基準留在 `BuildLegacySelects`，只給靜態比對與既有檢查使用，正式公布不呼叫它。手寫測試若只填 `Selects`、沒有 `Students`，必須另外指定測試用的舊清單旗標，公布方法才會使用 `UNION ALL`。正式畫面呼叫沒有這個旗標，缺了 JSON 學生就停止，不悄悄改回舊清單。

大量 JSON 在既有 `BackgroundWorker` 的 `SemesterRankPublishSql.Build` 裡組成。畫面執行緒只建立學生物件。不把排名拆成每 100 人一批。

成績 CTE、四張排名表欄位與失敗回復不在本次修改範圍。學期成績的 `rank_batch_student` 插入原本就沒有 `matrix_dept`，這次不補上。

## Risks / Trade-offs

- [舊批次沒有無成績學生] → 無快照還原會少人，並在批次層級提示；不能用目前名冊補回。
- [科別只存在科排名名稱] → 沒有科排名列就空白且不參與；不用目前科別填。
- [同一學生同一排名類型有多個名稱] → 不任取一筆、不用目前資料覆蓋；該項空白且不參與，並在確認清單列出全部衝突名稱。舊批次不修改。
- [`QueryHelper` 沒有跨呼叫交易] → 停用與啟用放在同一次 `Select` 的同一句。句失敗由資料庫整句回復。無法送出這一句時停止，不逐年級公布。
- [唯一約束不允許新舊列並存，或單句超過閘道長度] → 停止公布並回報。不改舊列母群名稱、不刪舊批次，也不逐年級提交。
- [程序在公布句送出前中斷] → 舊有效排名不變。若已有未生效批次，檢索看不到；清理只刪該批未生效資料。
- [Excel 再匯入會重套不排名預設] → 13 欄與學號加狀態的對應保持不變，但符合類別者的初始參與可能與匯出檔不同。
- [歷史快照沒有學生狀態] → JSON 與舊 XML 都不存學生狀態，也不存不排名類別。JSON 另存姓名，以及可解析的 `grade_year` 或 null。匯出時對缺值的 `student.id` 一次查目前 `student.status`。查不到、查詢失敗或不在六種值內就回報，不寫成一般，也不用學號猜測。
- [新批次不再把快照寫進 setting] → 只認得 XML 快照的舊程式會把新批次看成沒有快照。新程式先讀 extension，再讀舊 XML。
- [沒有快照時不從排名明細補科別] → 科別只讀 `matrix_dept`。學期成績插入沒有寫這個欄位時，科別留白、不參與並提示。
- [歷史加入學生仍只看學號] → Task 5.5 這次不改。相同學號多位學生會被擋住；清單裡不同 `student.id` 但學號相同時，舊去重可能誤判。日後以 `student.id` 為確認清單唯一識別。
- [多標籤 `First()` 順序不固定] → 依決策保留。相容比對時以同一次執行的名單為準，不預期與過去任意一次完全相同。
- [`K12.Data` 與 `Class` 等關聯屬性尚未確認可離緒] → Phase 8 先做確認。未確認前讀取留在 UI 執行緒，階段文字先顯示。不把未確認的呼叫放進背景工作。
- [學校擇優設定在排名語句前寫入] → 確認框說明它不會隨排名語句回復。順序維持 Task 4.2 的檢查，不在解除閘門時順手移動。沒有可計算年級時不呼叫 `cd.Save()`。
- [學生清單 JSON 很大] → 只組成一份，放在背景工作的同一句 SQL。不另存進 extension，也不在正式路徑同時產生每位學生的 SELECT。實際資料庫解析時間未測之前，不宣稱變快。
- [同一學生識別重複] → 正式清單直接停止。舊版會產生兩列並可能把成績 JOIN 兩次；比較基準仍保留那個行為，正式計算不再靜默取第一筆。
- [姓名含分號] → 既有單一敘述檢查會拒絕整句。這不是新的放寬，也不改成多句 SQL。
- [計算中改參與或加入學生] → 背景工作只讀計算開始時的工作副本。執行中旗標拒絕後續編輯，確定後才停用對應控制項，結束時恢復原本的可用與可見狀態。
- [失敗語句會中止 PostgreSQL 交易] → 測試以儲存點回復或獨立交易解除中止後再查。產品語句仍是單句，不在 `QueryHelper` 送出交易控制。
- [三項歷史來源遺留] → 維持獨立：無班級新增學生的年排名名稱空白但初始參與為 true；加入學生時讀取全部標籤；衝突名稱進快照時只留空白與不參與。Phase 8～11 不處理。

## Migration Plan

- 不執行資料表遷移，也不新增欄位。`extension` 使用既有 JSONB 陣列。
- 舊批次的 XML 版本 1 仍可讀。沒有 JSON 也沒有 XML 時，仍可用 `rank_batch_student` 讀取。
- 回復應用程式版本時，舊程式仍可讀新批次的排名明細與 setting 計算節點；它不會解讀 extension 裡的快照，也不會誤用批次 ID 0。
- 公布失敗時，由資料庫回復同一句；不另用第二個連線補救已經提交的有效排名切換。不建立預存程序。

## 2026-11-16 學期成績批次

1.0.0.63 複測後，學期排名設定頁不再把定期評量批次當母群來源。`SemesterHistoryBatchCatalog.TryClassifyExam` 只接受「學期成績」。`HistorySnapshotRestore.Load` 原本就拒絕其他考試名稱；`LoadSemester` 改為同一標準，下一步在讀學生前再驗所選批次的期間與類型。排序、快照標示，以及 JSON、XML、`rank_batch_student` 的還原順序不變。

計算期間由歷史與 Excel 共用。目前學生來源仍恢復系統學年期並停用欄位；離開時先記住可編輯期間，切回歷史或 Excel 再顯示回來。歷史年或學期一變，就清掉批次選取。沒有學期成績批次時，左下角顯示「此期間無學期成績批次」並停用下一步。

Excel 空白範本只寫 13 欄表頭，A 欄文字格式。示意與錯誤規則放在填寫說明，不放進活頁簿。確認清單新增唯讀「預設原因」；它讀進入清單時的 `MatchesExcludedCategory`，之後改參與不會清掉這段文字。

## 2026-11-17 無快照分頁

1.0.0.64 的「歷史批次設定讀取失敗」把期間核對、設定與快照、`StudentTag.SelectAll()`、`LoadSemester`、`SelectBatchStudentSql` 包在同一個例外裡。批次 285 走完前三段與快照還原就返回，而且確認頁有 1,363 人；91 與 283 沒有快照，才會執行最後那段整表查詢並出現 `Java heap space`。設定與標籤不是這次的失敗點，所以不改 `StudentTag.SelectAll()`，也不截斷 `setting` 或 `extension`。

分頁只發生在無快照分支。先送一筆 `count(id)` 與 `count(DISTINCT id)`，兩者不同就停止。相同才在資料庫把同一學生、同一學號、同一姓名、清理後五種母群名稱都相同的列收成一列。空白與非空白仍是不同觀察值。代表列的年級與 `id` 沿用該群原本的排序鍵；分頁游標則是該群最小的 `id`。外層是 `WHERE cursor_id > 上一頁最後的游標 ORDER BY cursor_id LIMIT 500`。500 是產品頁面大小；測試可以改成 1 列來驗證跨頁合併。不把整批原始列一次送回，也不只把每頁筆數放大。某一頁失敗時丟掉已累積的列，不呼叫合併，也不開啟確認頁。下一步的紀錄分成期間核對、批次設定與快照、學生標籤、歷史學生。歷史學生再分開記查詢耗時、合併耗時、頁數與回傳筆數。紀錄只留批次 ID、步驟、耗時、筆數、設定與延伸內容的字元數，以及例外文字。

設定頁用 `ShowDialog` 開啟，關閉時窗體通常還沒 `Dispose`。關閉會讓當次歷史載入失效。進度與完成回呼都要確認仍是這一次載入，才更新畫面、顯示錯誤或開啟確認頁。已經送出的查詢若不能中斷，返回後就停止後面的分頁與合併。找不到設定，或快照與排名學生無法還原時，只清掉那一筆選取並停用下一步，不清空整份批次清單。

載入一開始先把確認請求固定下來，快照成功與無快照成功都用這一份，完成時不再讀畫面上的批次。載入期間鎖住母群來源、歷史學年期與批次、計算學年期、計算年級、不排名學生類別和擇優採計；右上角關閉鈕仍可關。完成、失敗或啟動例外後才依原本規則恢復。期間核對不符、找不到設定、快照無法還原、無快照資料無法還原與分頁失敗，都留在設定頁，訊息含批次 ID、步驟與原因，清掉該筆選取並停用下一步。已關閉的舊工作只結束，不更新畫面、不顯示訊息、不開確認頁。

### 10. 學期專用流程套用政策

這次只改學期成績固定排名。畫面入口是 `Program.cs`「學期成績排名計算」，建立 `CalculateSemesterAssessmentRank`。不修改 `CalculateRegularAssessmentRank` 與技職繁星檔案，不發布 DLL，不寫入正式資料庫。

`CalculationPeriod`、`CalculationPeriodBinder`、`SemesterHistoryBatchCatalog`、`HistorySnapshotRestore`、`HistoryRankRestore` 與 `MotherGroupInitialParticipation` 放在 `MotherGroup`，但目前正式呼叫歷史清單與還原的是學期畫面。定期評量計算沒有呼叫這些類型，所以調整學期歷史政策不會改變定期評量目前的計算結果。定期評量 worktree `C:\ischoolProject\SHEvaluation-Regular` 不在本次修改或整合範圍。

仍優先由學期歷史流程套用新政策，不改共用預設：

- 無 JSON 的年、科、班參與目標，日後只加在學期歷史還原之後。不改 `MotherGroupInitialParticipation`，因此目前學生、Excel 與已有快照的初始規則維持原狀。
- `CalculationPeriod.ClearHistoryBatch()` 目前同時清掉批次 ID 與歷史期間。期間變更只應清批次，不應把使用者剛選的期間清掉。這次新增學期流程用的分開操作；在呼叫點一起改完前，不改這個方法的既有語意。
- `HistorySnapshotRestore` 目前拒絕考試名稱不是「學期成績」的批次。目錄納入定期評量後，下一步必須接受目錄已經接受的同一批。允許名單由學期歷史政策傳入，不把「只准學期成績」從整個共用預設直接刪掉。
- 離開歷史來源時清除批次選取與批次 ID。歷史期間首次使用 `_DefaultSchoolYear`、`_DefaultSemester` 所建立的初始計算期間，取代原本寫死的 1-1。每次載入歷史批次前同步欄位到模型並以兩欄篩選。切回保留仍維持現有控制項行為，不另新增記憶機制。

資料流方向是單向的：歷史學年度與學期是篩選條件，批次是選取結果。選到批次後，不把該批期間寫回篩選條件，也不額外寫回本次計算期間。切換歷史期間時清除不符合的選取與批次 ID。查詢失敗、零筆、重選與清除都要關掉殘留選取，不能繼續用上一個期間的批次。按下一步前再讀一次所選批次的學年度、學期，與畫面上的歷史期間不一致就停止。切換母群來源時，計算期間仍走該來源既有政策：目前學生來源恢復系統期間並停用欄位；歷史與 Excel 保持可編輯。

### 11. 已確認與尚未核准

已確認，可寫進規格：

- 只有歷史來源啟用歷史學年度、歷史學期與批次選取。
- 歷史期間與批次選取不額外覆寫本次計算期間；成績仍用切換來源後、依該來源既有政策得到的計算期間。目前學生來源恢復系統期間並停用欄位。
- 清單依歷史期間篩選，並在下一步再次核對。
- 學期成績與符合下方辨識的定期評量批次可選；技職繁星不選。
- 不改排名公式、成績擇優與正式寫入規則，不更新舊批次。
- 排序繼續使用 `rank_batch.id` 數字降冪。現行程式沒有建立時間欄位，不能把這個順序稱作建立時間。

2026-11-02 後續已確認，可寫進規格並實作：

- 「沒有 JSON」包含仍有 XML 版本 1、以及 JSON 與 XML 都沒有的批次。有效 JSON 才走既有快照還原，並維持五種參與的既有規則。
- 只有 XML 時，學生清單取自該 XML 的完整名單。XML 有學生 A、B，而 `rank_batch_student` 只有 A 或沒有列時，第二畫面仍保留 A、B。只有兩種快照都不存在時，才用 `rank_batch_student`。年、科、班不沿用歷史參與狀態，第二畫面顯示的名稱就是分組依據。不符合不排名類別者，相同名稱預設勾選參與。不用目前學籍補名稱。
- 年級邊界維持既有計算：年排名與科排名窗口已含 `rank_grade_year`，班排名窗口仍只依班名。不改這些窗口，也不把「高一甲」與「高二甲」收成同一個「甲」，或把不同年級的同名科別合成一個新名稱。
- 空白或名稱衝突不跳出 MessageBox、不移除學生、不自動取消年、科、班參與。衝突名稱留在確認清單的衝突欄，不任取一筆，也不開放名稱編輯，不用目前學生資料補名稱或年級。
- 計算使用第二畫面最終確認的名稱與參與狀態。類別一、類別二維持既有初始規則。

仍暫緩，規格寫明現況，任務不得改成另一種政策：

- 歷史期間初始值於 2026-11-03 已確認使用系統預設期間，不再列為未決；離開後切回是否重設仍未新增政策，保持現有欄位行為，批次選取清除。
- 不排名類別對無 JSON 年、科、班的優先序尚未核准。建議：可以，順序與其他來源相同，先得到本次初始參與，再套用圖1不排名類別，使用者仍可在第二畫面勾回。核准前，程式暫時保留既有不排名效果：符合者的年、科、班不自動改成參與；不符合者套用全參與預設。這不是已核准政策，也不是「核准前一律維持全參與」。類別一、類別二仍走原規則。
- 手動還原參與的基準。建議：回到進入第二畫面時的初始參與，不回到資料庫裡的歷史參與旗標。這與既有還原機制相同，所以不另做第二套基準。因此符合不排名類別者還原後仍是不參與，不符合者的年、科、班還原後仍是預設參與。另一套基準尚未核准。

JSON 存在但損壞、版本不支援或學生內容無效時，沿用既有停止規則，不降級成 XML、排名學生或全參與。排序維持 `rank_batch.id` 數字降冪，不稱作建立時間。

### 12. 批次辨識與顯示

以下來自靜態閱讀，尚未連線核對學校資料。

`rank_batch` 的學期與定期評量插入欄位是 `school_year`、`semester`、`calculation_description`、`setting`；學期新批次另可寫 `extension`。這兩段插入都沒有把 `ref_exam_id` 寫進 `rank_batch`。定期評量的考試 ID 只出現在後續排名列。因此不能靠 `rank_batch.ref_exam_id` 分辨來源。

`setting` 根節點必須是 `Setting`：

- 屬性「考試名稱」等於「學期成績」：學期成績。寫入點是 `CalculateSemesterAssessmentRank` 與 `SemesterRankPublishSql`。
- 屬性「考試名稱」有值，而且不是「學期成績」：定期評量。本專案只有 `CalculateRegularAssessmentRank` 會把考試名稱寫成實際評量名稱，說明文字是「學年度 學期 計算評量名稱排名」。
- 沒有「考試名稱」或值是空白：排除。技職繁星兩個 Step2 的 `Setting` 沒有這個屬性，另有年級與小數位數。只刪除「必須等於學期成績」會把這類批次放進來，所以不採用。

顯示文字：

`{id}｜{學期成績或定期評量}｜{學年度}學年度第{學期}學期｜{考試名稱}｜{calculation_description}｜年級{grades}｜快照有(JSON)、快照有(XML)或快照無`

例如：`120｜定期評量｜113學年度第2學期｜期中考｜113 2 計算期中考排名｜年級1、2｜快照無`

快照標示沿用既有規則：JSON 優先於 XML；JSON 文件損壞或版本不是 1 仍標成 JSON，不得標成沒有快照。年級仍從 `setting` 的「年級」元素讀取。清單可以標成快照有(XML)，但沒有有效 JSON 時，還原不讀這份 XML 的年、科、班參與，改以歷史學生清單套用決策 11。損壞的 JSON 仍停止，不走這條路。

實作前用獨立測試庫做唯讀查詢，確認沒有其他功能寫出非空白、且不是「學期成績」的考試名稱。這項沒有執行前，不能把辨識規則標成已用資料庫證明。
